Workflow

From IED model to HMI-ready output in a controlled sequence.

ARServer keeps the setup path explicit: choose the IED source, select SCADA-friendly signals, validate readability, map outputs, then start runtime.

01

Add by IP or open SCL

Connect to a live IED endpoint over MMS port 102 or import CID/SCD/ICD/IID engineering files.

02

Select useful signals

Prioritize breaker position, alarms, protection start/trip, status, and measurements.

03

Probe before runtime

Confirm selected object references are readable and decode value, quality, and timestamp sidecars when available.

04

Publish outputs

Build deterministic Modbus TCP addresses and optional MQTT topics from the same runtime cache.

Architecture

Relay data enters once, then fans out to the systems that need it.

ARServer sits between IEC 61850 IEDs and practical consuming systems. It keeps the relay read path controlled, then exposes selected values to classic control systems through Modbus TCP and modern data workflows through MQTT.

  • Relay / IED remains the source of truth over IEC 61850 MMS.
  • ARServer validates selected values before publishing outputs.
  • DCS, HMI, and SCADA tools can poll the Modbus TCP server.
  • IoT dashboards, middleware, or historians can subscribe through MQTT.

FAQ

Common questions before trying ARServer.

What is ARServer in simple terms?

ARServer is a Windows gateway that reads selected IEC 61850 relay or IED values and republishes them as Modbus TCP registers and MQTT topics for HMI, SCADA, DCS, dashboard, or test tools.

Is ARServer a relay test set?

No. It is not an Omicron-style relay test set and it does not inject protection signals. It is a gateway and engineering workspace for selected data reading, mapping, publishing, and validation.

Can it connect to a real relay or IED?

Yes, the intended workflow is to connect to an IEC 61850 MMS endpoint over TCP port 102 when the network, relay settings, and supported services allow it. Always validate on a safe bench or FAT network first.

Can it work without SCL files?

Yes. Add by IP supports online discovery for supported IEDs. SCL/CID/SCD/ICD/IID files are useful when engineering files are available and deterministic planning matters.

What is the difference between IEC 61850, Modbus TCP, and MQTT here?

IEC 61850 is the source protocol from the relay or IED. Modbus TCP is a polling interface commonly understood by DCS, HMI, and SCADA tools. MQTT is a publish/subscribe route for dashboards, middleware, historians, and IoT-style workflows.

Can FUXA, HMI, SCADA, or DCS connect to it?

Yes. Configure the external tool as a Modbus TCP client and point it to the PC running ARServer using the configured port, unit ID, and register map.

Do I need an MQTT broker?

Yes for MQTT output. ARServer publishes to a broker such as Mosquitto, EMQX, HiveMQ, or another MQTT broker. Modbus TCP output does not require MQTT.

Does ARServer send controls to the relay?

The current focus is read-only gateway operation. Control/write support should only be added with strict safety checks, operator confirmation, role separation, and test evidence.

What happens if relay communication is lost?

The runtime should make communication state, stale value risk, quality, and diagnostic status visible so an HMI user does not mistake old data for fresh relay data.

Why are quality and timestamp important?

A Boolean value without quality and timestamp can mislead operators. ARServer keeps value context visible so users can see whether a point is fresh, stale, good, invalid, or only locally updated.

Is it ready for production substations?

Treat it as an engineering gateway that must be validated for each environment. Production use requires controlled network design, cybersecurity review, redundancy decisions, change control, and site acceptance evidence.

What license does ARServer use?

The repository is released under Apache-2.0, so users can inspect, build, fork, and adapt the source according to the license terms.
